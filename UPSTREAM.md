# Upstream

Fork of [github/cmark-gfm](https://github.com/github/cmark-gfm) at `0.29.0.gfm.13`, the latest release as of 2026 (from Jul 21, 2023).

## Why this fork exists

Three reasons.

1. `Package.swift`, so the library can be consumed by Swift Package Manager. Upstream builds with CMake only.

2. Source-position fixes. `cmark-gfm` forked from [commonmark/cmark](https://github.com/commonmark/cmark) in 2019 and has not tracked it since; several sourcepos corrections upstream cmark has made were never merged back. Both `cmark-gfm` and the fork at [swiftlang/swift-cmark](https://github.com/swiftlang/swift-cmark) are largely dormant. The fixes below are backported from `cmark`, some cross-checked against the ones `swift-cmark` had already taken, and some our own.

3. Records for editors. The parser finds things it keeps no node for, like link reference definitions, and an editor that has to find them again on its own can disagree with it. The fork records them on the document, without changing any output (see *Records for editors* below).

## Changes from 0.29.0.gfm.13

### Packaging

- `Package.swift` and the layout changes SPM requires. *[1ff0c09088d40cd983419bda52284cf91c27fef5]*

### Backported source-position fixes

In order of commit (with *[SHA]* signatures).

- **Unmatched backtick runs** (`src/inlines.c`, `handle_backticks`) — reported `(pos, pos)` after rewinding, placing a run of *n* backticks as a single  column just past itself. Now reports the run's real span. *Example:* ` ```foo`` ` reported `(1,2)-(1,4)` for an eight-character literal. *[a88352ddca4f4b3c74b71291e568df1ce653c7b3]*

- **Autolink columns** (`src/inlines.c`, `make_autolink`) — omitted `subj->column_offset` and `subj->block_offset`, so `<https://example.com>` reported columns in the block's frame rather than the line's. Wrong by the width of every stripped prefix inside a blockquote, list item, or indented block. *Example:* `- <https://example.com>`. *[0f00e56e33be0edf634f3827c5161b937a3541a8]*

- **Link start line** (`src/inlines.c`, `handle_close_bracket`) — set `start_line` to the line holding `]` while taking `start_column` from the opening bracket, so a link spanning lines reported a start whose line and column came from different places. Now takes both from the opener.\
  *Example:* `[a \n  link](https://example.com)`. *[0d63fea4d3976411488678e57c9e82ce4f812563]*

- **Block end lines** (`src/blocks.c`, `finalize` and `add_line`) — `finalize` assumed blocks are closed from a later line and set `end_line` to `parser->line_number - 1`. HTML blocks of types 1–5 end on a condition inside a line and are finalized while still on it, so they reported `(0, 0)`. `swift-cmark`'s guard on that branch is taken here, but it relies on `end_line` holding the last line the block consumed, and upstream only ever sets it in `add_child`. Setting it in `add_line` as well completes the fix. *Example:* `<style>\np{color:red;}\n</style>` reported `(1,1)-(2,13)` for a three-line block; `<!DOCTYPE html>` reported `(1,1)-(0,0)`. *[66c52a391df961e3a7cdb10e7dd7d355ebcffb20]*

- **Backslash hard break line tracking** (`src/inlines.c`, `handle_backslash`) — the linebreak branch calls `skip_line_end`, which only advances `subj->pos`. Unlike `handle_newline`, it never advances `subj->line` or resets `column_offset`, so everything after a backslash hard break keeps measuring from the line it was on before the break. *Example:* `foo\` followed by `bar` on the next line reported `bar` on line 1. *[bc6fdad044af324bb9caa3ca5737effeeaced41b]*

- **Raw HTML delimiter width** (`src/inlines.c`, `handle_pointy_brace`) — called `adjust_subj_node_newlines` with `extra=1`, the value `handle_backticks` uses to exclude a code span's closing backticks from its end position. Raw HTML's own position is delimiter-inclusive, so the same `extra` wrongly excluded its closing `>` too. *Example:* `<a href="foo\nbar">` reported its end one character short of the `>`. *[d13ae44c7a20fe33a6c17a3ad75052d48cfc9f48]*

- **Multi-line construct end column missing block_offset** (`src/inlines.c`, `adjust_subj_node_newlines`) — `end_column` was set to `since_newline` directly, skipping the `+ subj->block_offset` every other column assignment in this file includes. Invisible at the top level, where `block_offset` is 0; wrong by the container's prefix width for a code span or HTML tag nested inside a blockquote or list item. *Example:* `` `bl\nah` `` spanning two lines inside `> ` reported its closing backtick two columns short. *[668ac2b7a4bde51b7b5b7d0fe628b7ce93aabc95]*

- **Table header under a paragraph** (`extensions/table.c`, `try_opening_table_header`; `src/blocks.c`, `add_line`) — GFM lets a table's header row be the last line of a paragraph, which is only known once the delimiter row arrives. The extension turned the whole paragraph into the table and copied the lines above the header into a new paragraph made with `cmark_node_new_with_mem`. That copy had no position (`0:0-0:0`, its inlines numbered from line 0), and the table, its header row and header cells kept the paragraph's first line, with the cells measured along all of the paragraph's text. Now the header row is taken off the end of the paragraph and the table is opened after it with `cmark_parser_add_child`, as any block that interrupts a paragraph is: the paragraph stays the parser's own node, with its real start, and the table starts on the header's line. `finalize` ends a block on the line before the one that closed it, which here is the header's, so the paragraph's end is set to the line before that. Both numbers this needs are from lines the parser has already finished with, so `add_line` records them: where the added line's text starts (`last_added_line_offset`) and the length of the line before it (`line_length_before_last_added`). *Example:* `adasda` above `| a | b |` reported the paragraph at `0:0-0:0` and the first header cell at `1:9-1:11`; now `1:1-1:6` and `2:2-2:4`. *[8a566397be755d9086446fcfae2fd62c43bc0091]*

- **Line endings after a link's text** (`src/inlines.c`, `handle_close_bracket`) — between a link's `]` and its end, an inline link's destination and title are read with `scan_spacechars`, `manual_scan_link_url` and `scan_link_title`, and a full reference link's label with `link_label`. All of them only advance `subj->pos`, so a line ending there never advanced `subj->line` or reset `column_offset`, and the link's end and everything after it were measured along the line before. Now the line endings in that stretch are counted with `adjust_subj_node_newlines`, with `extra=0`, since a link's position includes its closing `)` or `]`, as raw HTML's includes its `>`. The link text's own line endings already went through `handle_newline`. Upstream cmark has the same gap. Images take the same path. *Example:* `[b](\nc.md) d` reported the link at `(1,1)-(1,10)` and ` d` at `(1,11)-(1,12)`; now `(1,1)-(2,5)` and `(2,6)-(2,7)`. *[4bc8935f52341c6441449ae7c619b5e3a09092c2]*

- **Columns on a block's later lines** (`src/blocks.c`, `add_line` and `resolve_reference_link_definitions`; `src/inlines.c`, `handle_newline`, `handle_backslash`, `adjust_subj_node_newlines` and `cmark_parse_inlines`; `src/node.h`) — an inline's column was its offset into its line of the block's text plus `block_offset`, where the block's *first* line starts. Every later line has its own container prefix and indentation taken off, by however much that line matched (`check_open_blocks`), so inlines on it were off by the difference: inside a block quote, a list item, on lazy lines, and after indentation. `add_line` now records where each line's text starts in its source line (`line_starts`, for paragraphs and headings), definitions taken off a paragraph take their lines' starts with them, and the inline parser measures each line from its own start (`start_line`). Table cells keep no line starts and are unchanged. The starts are freed once the block's inlines are parsed. Upstream cmark has the same arithmetic. Output is unchanged. *Example:* `> a` then `>  b` reported `b` at `2:3`; now `2:4`. `Foo` then `    bar` reported `bar` at `2:1`; now `2:5`. *[7b53235ceca96ef2d67ad58dc4259ce3859a63fa]*

- **A block's start after its definitions** (`src/blocks.c`, `resolve_reference_link_definitions` and `add_line_start`) — definitions at the start of a paragraph are taken off its text, but the paragraph kept the start of its first line, which was the first definition's. Its inlines were numbered from that line too, so everything in it was reported that many lines high. A setext heading made from what was left had the same start. Now the block starts on the line after the definitions, at where that line's text starts. A paragraph left with no text, when the next line is added to it rather than ending it (`===` under a definition), starts at that line's text. ATX headings never hold definitions and are unchanged. Upstream cmark has the same gap. Output is unchanged. *Example:* `> [a]: /u` then `*x*` reported the paragraph at `1:3` and the emphasis at `1:1-1:3`; now `2:1` and `2:1-2:3`. *[eee7cf5afbb183056f7bba4df8f82110b3ba411c]*

- **Ends of setext headings and fenced code** (`src/blocks.c`, `finalize` and `parse_code_block_prefix`) — `finalize` ended a setext heading or a fenced code block on the line it was finalized from, as if that were always the line that closed it. Only a closing fence closes a block on its own line. A setext heading is finalized from the line after its underline, and a fenced code block whose container ends it from the line after its last, so both reported that next line as their end: a heading overlapped the block after it, and a code block reached past its own block quote or list item. Now the closing fence sets the block's `end_line` to its own line, and both go through the check the HTML block fix added (`line_number - 1 < end_line`), which tells a block finalized on its last line from one finalized after it. Upstream cmark has the same code. Output is unchanged. *Example:* `Foo`, `---`, `bar` reported the heading at `1:1-3:3`; now `1:1-2:3`. `> ``` `, `> a`, `b` reported the code block at `1:3-3:1`, outside its quote's `1:1-2:3`; now `1:3-2:3`. *[5829b4d483b7d2867c59cff6fc93f8a35a586dca]*

### Fixes that change output

- **Link reference definitions above a table header** (same change as above) — the paragraph copy never went through `finalize`, so link reference definitions at its start were never taken off: they rendered as text, and links using them didn't resolve. It also unescaped `\|` in the copy's text, which only cells need, so every column after one was a byte short (output unaffected, since `\|` in a paragraph is an escape either way). Both went with the copy. *Example:* `[ref]: /url` and `foo` above `| a |` rendered `<p>[ref]: /url\nfoo</p>`, and `[x][ref]` later in the document stayed text. *[8a566397be755d9086446fcfae2fd62c43bc0091]*

- **Leading spaces of a lazy continuation line** (`src/blocks.c`, `add_text_to_container`) — backported from upstream cmark `1252411`. A paragraph line's leading spaces and tabs aren't part of its text (spec 4.8), and cmark skipped them for a normal continuation line, but added a lazy one from where container matching stopped, so its leading spaces stayed in the text. They showed in a code span, where the line ending becomes a space, and after a backslash hard break, where they became text. Now the lazy line skips to its first non-space too. Its line start is recorded after the skip, so positions follow. *Example:* `> \`a` then ` b\`` rendered `<code>a  b</code>`, now `<code>a b</code>`; `> a\` then `  b` rendered `<br />\n  b`, now `<br />\nb`. *[bbc49cabdb624369b2d80c82699ff73e5522dd31]*

- **A definition's title followed by other text** (`src/inlines.c`, `cmark_parse_reference_inline`) — backported from upstream cmark `7042d99`. When what follows a title on its line isn't the line's end, the title isn't part of the definition, and parsing rewinds to before it. The title already scanned was still kept, so links using the definition got it. Now it's dropped on that path. *Example:* `[bla]: /bla`, `"The title" garbage`, `[bla]` gave `<a href="/bla" title="The title">`; now `<a href="/bla">`. *[574e68c714c83d453cd5b934f9a3edc996461f81]*

- **A line ending in a `<…>` destination** (`src/inlines.c`, `manual_scan_link_url`) — backported from upstream cmark `067e1fd`. A destination in pointy brackets can't hold a line ending, but a backslash right before one let it through, as an escape of the line ending. Now that ends the destination's scan, and there's no link. *Example:* `[a](<b\` then `c>)` was a link to `b%5C%0Ac`; now it's text with a hard break. *[e3680e9ef256ef9f651f4c2e0e8f43da400f14bc]*

- **A thematic break after a definition** (`src/blocks.c`, `open_new_blocks`) — backported from upstream cmark `6566d91`. A line of `-` under a paragraph is a setext underline only when text is left once the paragraph's definitions are taken off. The check took them off, but when nothing was left, the line was never looked at again as a thematic break, and stayed paragraph text. Now the setext branch is taken only when text is left, and otherwise the line goes on to the thematic break check. *Example:* `[f]:r` then `---` rendered `<p>---</p>`; now `<hr />`. *[ea6f0b193e74816a0aab5205fca47682749895f5]*

- **A list item whose only paragraph was a definition** (`src/blocks.c`, `finalize` and `parse_node_item_prefix`; `src/node.h`) — backported from upstream cmark `8c9c5e4`. A paragraph holding only definitions is removed when it closes, leaving its list item with no children, which `parse_node_item_prefix` took to mean the item opened on a blank line. A later blank line indented less than the item's content then ended the item, though a line indented enough after it still belonged to it. Now the item is marked when such a paragraph is removed (`CMARK_NODE__ITEM_HAD_CONTENT`), and kept open as an item with children is. Upstream's flag takes `1 << 4`; here `1 << 3` is free, and `CMARK_NODE__REGISTER_FIRST`, where extensions' flags start, moves to `1 << 4`. *Example:* `- [r]:x`, a blank line, ` `, `  l` rendered an empty item and `<p>l</p>` after the list; now `<li>l</li>`. *[21a7a87f4bd3328fa5021ef5e9e9be0ab849d85e]*

### Thread safety

- **Extension characters kept per parser** (`src/inlines.c`, `src/inlines.h`, `src/blocks.c`, `src/parser.h`) — the characters an inline extension starts with (`~` for strikethrough, `:` and `w` for autolinks) were added to the file-level `SPECIAL_CHARS` and `SKIP_CHARS` tables at the start of every parse's inline phase and removed at its end (`cmark_manage_extensions_special_characters`, called from `process_inlines`). Two parsers running at once on different threads added and removed them under each other, so a parse could lose them partway through and miss strikethrough and autolinks. Now each parser holds its own two tables (`special_chars`, `skip_chars`) for its extensions' characters, and `SPECIAL_CHARS` holds only the characters inline parsing always stops at, as a constant. `subject_find_special_char`, `scan_delims` and `handle_delim` take the parser to read them. `cmark_manage_extensions_special_characters` keeps its public signature. Same idea as `swift-cmark`'s, smaller: it only adds the extensions' characters to the parser, so there's no copying of defaults and nothing to allocate. Output is unchanged for one parser at a time. *Example:* four threads each parsing `a ~~b~~ c www.example.com` 20,000 times gave the wrong HTML 23,759 times out of 80,000; now none. *[cf8bc06ad3f797003c211a565bc90fe81020a402]*

### Records for editors

Additions to the public API that give an editor what the parser finds and keeps no node for. They're recorded only when parsing with `CMARK_OPT_SOURCEPOS`, and change no output.

- **Link reference definitions** (`include/cmark-gfm.h`, `cmark_node_get_reference_definitions`, `cmark_reference_definition` and `cmark_source_range`; `src/blocks.c`, `resolve_reference_link_definitions`; `src/inlines.c`, `cmark_parse_reference_inline`; `src/node.h` and `src/node.c`) — a definition is taken off the start of its paragraph and leaves no node, so an editor that styles one, or points at a broken one, had to find it again itself, and could disagree with the parser: a definition in a block quote or list item, a definition-shaped line inside a code block or continuing a paragraph. Now the document holds every definition the parser took, in order, a label defined again included, with where its label, destination and title are, as `sourcepos` gives positions. `cmark_parse_reference_inline` reports where the parts are, and `resolve_reference_link_definitions` turns them into source positions with the paragraph's line starts (see *Columns on a block's later lines*) before taking the definitions off. They're kept on the document node (`as.document`) and freed with it. *Example:* `> [a]: /u` then `> [b]: /v` gives `a` at `1:4-1:4` with its destination at `1:8-1:9`, and `b` at `2:4-2:4`. *[SHA]*

## Not taken from swift-cmark

`swift-cmark` carries feature work for `swift-markdown` that this fork deliberately omits: the `^[...]` attribute syntax and `CMARK_NODE_ATTRIBUTE`, `CMARK_OPT_PRESERVE_WHITESPACE`, `bracket_type` replacing `bool image`, and `node->backtick_count`. These change parsing behaviour or the public node structure. Its per-parser character tables were taken in a smaller form (see *Thread safety* above).

## Known divergences from the GFM spec

Not yet fixed. Listed so they aren't rediscovered.

- Email autolinks are matched after inline parsing, over text where escapes and character references have already been resolved, so `<foo\+@bar.example.com>` produces a link the spec says should not exist (spec example 614). `www.` and `http://` are matched during inline parsing and are unaffected. Fixing it means moving email matching to parse time, which changes output rather than positions.
